# 2/4 진단·수정 제안 — 1·2단계

> 확인 관문에서 작가 답을 받은 뒤(선행 실행 대상 모드는 1/4 카드를 내기 전에) 읽는다. 독자·편집자 호출, 데스크 대조와 하네스, 진단 기록, 원고 블록 보기를 다룬다.
> 관문 출력 순서·작가용 표기·추천 요청 형식·가독성 규칙은 SKILL.md의 `관문 진행`을, 모드별 관문 수는 SKILL.md의 `모드`를 따른다. `{BASE}`는 이 스킬의 기준 경로다.

## 1. 진단 — 읽기 전용

독자와 편집자는 부모 대화를 모르는 새 문맥의 서브에이전트다(Agent 도구, `general-purpose`). 두 역할 모두 아래 **데스크 조건 블록**을 프롬프트에 그대로 받는다.

```text
조건(편집 데스크가 잠근 값 — 브리프의 기본값보다 우선):
- 채널:
- 글의 목적:
- 예상 독자: (원고의 실제 대상 독자. 브리프의 기본 독자상 대신 이 독자로 읽을 것)
- 중심 판단(바꾸지 말 것):
- 보존: (문단 번호 + 문장)
- 사실 확인 필요(새 수치·원인을 만들지 말 것):
- 원고별 용어집: (있으면 표 전문)
- 책 기준 경로: (책 원고일 때만. 집필 정본·공통 기준 절대 경로. voice보다 먼저 읽고 종결체·길이·구조·표기는 이것을 따를 것)
- 기초 수치: (check.py --stats 요약. 종결체 혼용·90자 이상·어두 반복·상투어 후보 위치. 출발점으로 쓰고 문맥으로 판정할 것)
- 문단 번호: 제목=0, 이후 빈 줄 기준 1부터 (check.py와 같은 번호)
- 등급: High·Mid 두 가지만 쓸 것
- 원고에 없는 사실·원인·경험이 필요한 자리는 '저자 확인'으로 따로 모을 것
```

**① 독자 호출.** `model: "sonnet"`으로 부른다. 독자는 반응과 막힘만 보고하고 수정문을 쓰지 않으므로 편집자보다 가벼운 모델로 충분하다. 심층 개선은 모델을 지정하지 않는다(기본 모델). 넘길 것: `{BASE}/roles/reader.md` 절대 경로, 원고 절대 경로, 조건 블록, 리포트 저장 경로(임시 작업 폴더의 `독자리포트.md`). 반환: 독자 리포트만. 수정문 없음. 독자는 같은 리포트를 저장 경로에도 쓴다. `gate-1-intake.md`의 `진단 선행 실행`으로 이미 띄웠으면 다시 부르지 않는다.

**② 편집자 호출.** 독자 리포트가 돌아온 뒤 순차로 부른다. 모델은 지정하지 않는다(기본 모델). 선행 실행 중 독자가 작가 답보다 먼저 끝났으면 그때 백그라운드로 띄운다(`gate-1-intake.md`의 `진단 선행 실행` 3). 넘길 것:
- `{BASE}/roles/editor.md` 절대 경로
- voice 절대 경로: `01-voice`·`02-glossary`·`03-anti-traces`·`04-examples`. 원고가 3,000자 이하면 01·03만 넘기고 판정이 갈릴 때 02·04를 읽게 한다
- 책 원고면 0단계에서 찾은 책 기준 절대 경로(조건 블록의 `책 기준 경로`)
- 원고 절대 경로, 조건 블록, 독자 리포트 파일의 절대 경로, 편집 강도(기본 표준, 구조는 사용자가 명시했을 때만), 출력: 제안. 독자 리포트를 데스크가 요약해 옮겨 적지 않는다. 파일이 없을 때만 리포트 전문을 프롬프트에 넣는다
- `Skill` 도구를 쓰지 말고 받은 경로만 읽으라는 지시
- AI 흔적 지수는 `03-anti-traces.md` §11 정의로만 산출하라는 지시
- 완료 조건: 제안 3~5건, 각 건 `등급 / 선행 / 위치 / 현재 문장 / 수정 방향 완성 문장 / 이유`. 원고 전문을 다시 쓰지 않는다. 찾았지만 제안하지 않은 항목은 `보류 발견`에 현재 문장·보류 이유·대안 문장으로 모두 적는다. 저자 확인은 항목마다 A안(답 없이 성립하는 문장)·B안(답에 따른 문장)·분류 후보(필수·선택)를 적는다(브리프의 출력 형식에 들어 있으므로 프롬프트에 형식을 다시 쓰지 않는다)

편집자가 파일을 못 읽었다며 빈손으로 돌아오면 그대로 전달하지 않는다. `voice/00-minimum-card.md` 본문(없으면 아래 최소 카드)을 프롬프트에 넣어 다시 부른다.

**심층 개선**이면 독자와 편집자를 한 메시지에서 동시에 부른다. 편집자는 독자 리포트 없이 원고만 독립 편집하고, 데스크가 두 결과를 대조한다.

**서브에이전트를 부를 수 없는 환경**이면 데스크가 독자 → 편집자 순서로 두 브리프를 차례로 적용하고, 출력 말미에 `역할 수행: 데스크 단독 (서브에이전트 호출 불가)`를 적는다. 조용히 대신하지 않는다.

**데스크 대조.** 편집자 결과를 그대로 전달하지 않는다. 다음 일곱 축으로 원문과 대조한다.

| 축 | 점검 |
|---|---|
| 논지·구조 | 제목·도입·사례·마무리가 하나의 질문에 답하는가. 제목 범위는 다시 진단하지 않고 1/4 범위 판정을 따른다(`제목을 본문에 맞춤`이면 제목 문제는 이슈로 올리지 않고 4/4로 넘기고, `본문을 제목에 맞춤`이면 본문 쪽 범위 이슈를 High로 올린다). 1/4 판정 뒤 새로 드러난 범위 어긋남은 4/4 범위 재판정 입력으로 남긴다. 소제목끼리 같은 문형(행동·판단 문장)으로 짝을 이루는가. 문단마다 주된 역할(장면·설명·근거·판단·전환)이 하나인가. 결말이 새 교훈을 덧붙이거나 본문을 반복하지 않는가 |
| 독자 경로 | 첫 문단에서 읽을 이유가 생기는가. 전문용어·제품명·전제가 설명 없이 나오는가 |
| 신뢰 경계 | 경험·확인된 사실·판단·계획·추측이 구분되는가. 수치·인용·제품 기능 중 원문 대조가 필요한 위치는 어디인가. 숫자는 없지만 양·비율·빈도를 단정한 문장(`참석자 대부분이은`, `늘`, `모두`)에 잰 기준이 있는가. `check.py --stats`의 수량어 후보를 출발점으로 쓰되, 통념을 세우는 일반화(`대부분 ~로 본다`)는 이슈가 아니다 |
| 종결어미·화법 | 한 원고 안에서 ~다체와 ~합니다체가 문단 단위로 섞였는가. 섞인 문단은 문단 수정이므로 여기서 이슈로 잡는다. 1인칭으로 쓴 글에서 저자 자신을 `사용자`·`작가`·`우리` 같은 3인칭·복수로 부른 곳이 있는가 |
| 구조형 AI 흔적 | 제목·도입·결말이 같은 말을 되풀이하는가. 문단을 닫는 판단 문장이 `A가 아니라(보다) B` 틀로 세 번 이상 겹치는가(하나하나가 정당해도 반복이면 진단에 올린다). 독자 오해를 바로잡지 않는 `A가 아니라 B` 대비, 같은 전개·한 줄 결론 반복, 근거 없는 중요성 선언, 판단을 늦추는 예고문, 형식뿐인 세 항목 나열 |
| 새 주장 | 교체 문장이 원문에 없던 주장·비교·근거·저자 의도를 들여오는가. 끼워 넣은 문장이 다음 문장의 지시어(이런·그·이) 대상을 가로채는가. 주어를 바꾼 문장 때문에 다음 문장의 생략된 주어가 끊기는가. 확인 대기 사실을 걷어 낸 자리를 새 주장으로 메웠다면 대체문 없이 삭제하는 쪽으로 조정한다 |
| 강점 | 고치지 말아야 할 문장·장면·판단 |

이어서 제안 전체에 하네스 점검을 돌린다. 편집자가 자기 결과를 스스로 합격 처리하지 않도록 데스크가 다시 본다.

| 점검 | 합격 기준 |
|---|---|
| 금지어·상투어 | 제안 문장 0건 |
| 사실 보존 | 수치·고유명사·인용·날짜 불일치 0건 |
| AI 흔적 지수 | 제안 적용 시 수정 전 대비 하락. 편집자 지수와 `check.py` 상투어 후보 건수가 크게 어긋나면(한쪽 0, 다른 쪽 3건 이상) 위치를 대조해 누락·과잉을 바로잡는다 |
| 기초 수치 반영 | `--stats`의 종결체 혼용·90자 이상 문장을 이슈로 올렸거나 올리지 않은 이유가 있다 |
| 제안 적용 미리 대조 | 2/4에 낼 수정 후 문장(추천 `반영` + `작가 판단`)을 치환 목록으로 만들어 `check.py --apply 치환.json 원고.md 미리보기.md`를 돌린다. 원문 문장이 모두 1회씩 잡히고, 분량 120% 이내, 숫자 보존 일치, 90자 이상 문장이 새로 생기지 않는다 |
| 일반론 | 편집자가 사례를 지어 채우지 않고 `구체화 필요`로 남겼는가 |
| 문장 연결 | 수정 후 문장을 앞뒤 문장과 이어 읽었을 때 지시어 대상과 생략된 주어가 그대로 이어지는가(`roles/editor.md`의 `문장 연결 점검`). 데스크 조정 문장도 포함한다 |

미달 항목은 해당 제안만 편집자에게 되돌려 다시 받는다. 최대 2회, 그 뒤에도 남으면 위치와 사유를 이슈표에 적는다.

데스크가 편집자 문장을 합치거나 바꾼 `조정` 문장도 하네스 대상이다. 미리 대조에서 90자 이상 문장이 새로 나오면 문장을 나누고, 나눌 수 없으면 블록의 `조정:` 줄에 길이와 남기는 이유를 적는다(2026-11-10 실제 원고에서 데스크가 두 문장을 합쳐 123자 문장이 승인 문장으로 들어갔다). 2/4 `추천 요약`의 분량은 이 대조가 낸 값을 쓴다. 미리보기 파일은 대조 뒤 지우고, 치환 목록은 3단계에서 승인 항목만 남겨 다시 쓴다.

독자 반응은 `[원고근거]`와 `[독자추정]`으로 나눈다. `[독자추정]`만으로 원문 예시를 바꾸는 이슈를 만들지 않는다. 독자가 원고에 없는 사실·원인·경험을 물으면 이슈로 올리지 않고 `저자 확인`으로 분리한다.

**보류 발견 올리기.** 편집자가 찾았지만 `지수 낮음`·`의미를 싣고 있음` 등을 이유로 제안하지 않은 항목(편집 진단·총평에 적힌 것)은 데스크가 버리지 않는다. 7축 대조에서 직접 발견한 항목과 함께 제안 관문으로 올리고, 넣을지는 작가가 정하게 `(새로 올림)`을 붙인다. 편집자 안에 완성 문장이 없으면 데스크가 보류 발견에 적힌 대안을 쓰고, 대안도 없으면 편집자에게 그 항목만 되돌려 받는다.

**진단 기록.** 진단 하나를 아래 블록 하나로 내부에 기록한다. 제안 관문에서는 이 블록을 `왜` 한 줄로 압축해 보이고, 작가가 `진단 근거 보여줘`라고 하면 블록 전체를 낸다. `진단만` 모드의 마지막 출력도 이 블록으로 낸다.

```text
진단 1 · [6]·[7]→[10] · 스킬 정의가 늦게 나옴 (원고 근거)
- 현재: [6] "이런 내용까지 모두 스킬에 저장하면…" → 정의는 [10]에서 처음 나옴
- 문제: 스킬이 [6]·[7] 두 문단에서 정의 없이 쓰인다
- 독자에게 생기는 일: 스킬을 '저장해 둔 긴 프롬프트'로 짐작하고 [7]의 구분이 흐려진다
- 처리: 수정 1 (정의를 [6]으로 이동)
```

- 진단 제목 줄: `진단 N · 위치 · 문제를 한 구절로` + `(원고 근거)` 또는 `(추정)`. 편집자가 보류했다 데스크가 올린 것은 `새로 올림`을 붙인다.
- `현재`는 원고 문장을 그대로 인용한다. 여러 문장에 걸친 진단은 문장마다 한 줄씩 인용한다.
- `독자에게 생기는 일`은 독자 리포트의 반응을 근거로 쓴다. 독자 추정만 있으면 `(추정)`을 붙이고, 추정만으로 원문 예시를 바꾸는 처리를 적지 않는다.
- `처리`에는 제안 관문에서 쓸 `수정 N`, 저자 답이 필요한 `물음 N`, 교정 단계의 `교정`, 고치지 않는 `그대로` 중 하나를 적는다. 진단 번호와 수정 번호는 같은 순서로 맞추고, 같은 문장을 고치는 진단 둘은 수정 하나로 묶는다.
- 진단 상한은 High 3·Mid 5다. 넘으면 Mid를 위치 순으로 잘라 `더 본 곳: 위치 — 한 줄`로 남긴다.
- 작가에게 내는 진단 근거에는 `7축`·`하네스`·`[원고근거]`·`[독자추정]` 같은 내부 용어를 쓰지 않는다.

완료 기준: 모든 지적이 최신 원고의 실제 위치에 연결되고, 원문에 없는 결함을 추측해 만들지 않았다. 원고 변경 0건. 1단계에서는 멈추지 않고 2단계로 이어진다.

## 2. 진단·수정 제안 — 제안 관문

High 최대 3개, Mid 최대 5개(새로 올린 항목 포함), 유지할 강점 최대 3개. 문제가 없으면 개수를 채우지 않는다. 이슈 ID는 원고 단위로 `ED-01`부터 매기고 이후 라운드에서도 유지한다.

```text
ED-01 [High] 선행: 없음 · 연결: 없음
위치: 2문단 첫 문장
현재 문장: (원고에서 그대로 인용)
제안: 교체 / 이동 / 삭제 — (들어갈 완성 문장 또는 이동 위치)
이유: (독자 또는 논리 영향, [원고근거]/[독자추정] 표시)
보존 요소: (이 수정에서 지켜야 할 표현·경험)
추천: 반영 / 유지 — (한 줄 이유. 작가의 판단 강도와 관련된 선택이면 그 사실을 적는다)
```

위 블록은 내부 기록 형식이다. 작가에게는 **원고 블록 보기**로 낸다. 원고 순서대로 문단을 놓고, 바뀌는 문단마다 고치는 이유(`왜`)와 수정 전·수정 후 전문을 보인다. 작가는 고친 문장을 보면서 진단이 맞는지와 수정을 넣을지를 한 번에 정한다(2026-11-10 실제 원고에서 문장 조각 표 → 전후 문장 표 → 문단 블록 → 진단과 수정 블록 통합 순으로 바꿔 달라는 요청을 받아 확정한 형식).

```text
[2/4 진단·수정 제안 · 원고 블록 보기] 고칠 곳 N · 바뀌는 문단 N개 · 저자에게 물을 것 N(필수 N) · 다음은 수정 결과
지금 정할 것: 필수 물음의 답, 블록마다 반영 / 그대로 / 나중에. 왜가 틀렸다고 보면 그 수정은 그대로

필수 물음 — 답하면 결과 관문에서 바로 게시 가능 판정을 받을 수 있습니다
물음 1. 스킬은 어떤 도구에서 쓰고, 챗GPT 사용자에게도 해당합니까? → 답에 따라 수정 2의 주어가 정해집니다 (A안 "AI가" / B안 "클로드가")

표기: ~~지운 말~~ · **넣은 말**

**[0]~[4] 그대로**
[0] 제목(4/4에서 다룸) · [1] 클로드나 챗GPT로 글을… · [2] 블로그 글을 쓸 때…(지킬 문장) · …

**[14] "스킬을 쓴다고 결과물이" — 수정 6 · 좋음 · 작가 판단** (새로 올림)
- 왜: "~이 아니라 ~이다"로 맺는 판단이 네 번째로 나와 끝으로 갈수록 같은 틀이 반복되는 인상을 줍니다. (그대로 두는 곳: [7] "저장 여부보다", [11] "남길 기준을 골라")
> 수정 전: (문단 전문)
> 수정 후: (문단 전문, 바뀐 말만 표기)

**[6] "이런 내용까지 모두 스킬에" — 수정 1 · 꼭 · 반영 / 수정 3 · 좋음 · 반영**
- 왜(수정 1): 스킬이 정의 없이 쓰여, 처음 접하는 독자는 '스킬에 저장한다'가 어떤 행동인지 모른 채 넘어갑니다.
- 왜(수정 3): 문단 끝 문장이 저자의 판단이 아니라 독자에게 내리는 규칙처럼 들립니다.
> 수정 전: (문단 전문)
> 수정 후: (문단 전문, 바뀐 말만 표기)
- 조정: 편집자는 정의를 별도 문장으로 넣었지만 "이런 내용까지"가 정의 문장을 가리키게 되어 기존 문장 안에 넣었습니다.

**[13] "새 글을 시작할 때" — 수정 4 · 좋음 · 반영(A안)**
- 왜: …
> 수정 전 / 수정 후: …
- B안: 이 글을 실제로 그 프롬프트로 시작했다면 첫 문장을 "…"로 씁니다(물음 2).

추천 요약: 반영 1·2·3·4·5 · 작가 판단 6 · 분량 원문 대비 N% · 작가 판단 항목은 번호를 말해야 반영됩니다
진단에서 뺀 것: (원고 범위 밖이라 물음으로 돌린 것, 한 줄)
교정 단계로 넘길 것: (병기·기호 처리, 한 줄)
안전 점검: 금지어 N · 사실·수치 변경 N · AI 흔적 N.N → 제안 적용 시 N.N
선택 물음: 2) … (수정 N 보강) 3) …
지킬 강점: [2] 실제 지시문 예시 · [11] 마지막 · [15] 전체

다음 단계에서 하는 일: (관문 진행의 `제안 관문 → 수정 결과` 기본값)
```

- 제목 없이 접수한 원고는 [0]이 도입 문단이므로 다른 문단과 같이 2/4 블록으로 올린다. 아래 줄은 제목이 있는 원고에만 적용한다.
- 제목 [0]은 2/4에 블록으로 올리지 않는다. 그대로 묶음에 `제목(4/4에서 다룸)`으로만 적는다. 1/4에서 `본문을 제목에 맞춤`으로 정했을 때만 본문 쪽 수정이 2/4에 올라온다.
- 블록 머리: `[N] "원문 구절" — 수정 번호 · 등급(꼭·좋음·표기) · 추천(반영·그대로·작가 판단)`. 보류 발견에서 데스크가 올린 것은 `(새로 올림)`을 붙인다. 한 문단에 수정 둘 이상이 걸리면 `/`로 이어 적고 한 블록에 함께 반영해 보인다.
- `왜`는 수정 전·후보다 먼저 둔다. 수정 문장이 자연스러우면 진단을 따져 보지 않고 받아들이기 쉬워서, 이유를 먼저 읽게 한다.
- `왜`는 독자에게 생기는 일을 편집 용어 없이 한 줄로 쓴다. '대비 구문'·'당위 종결'·'권고 공식' 대신 독자가 읽으며 겪는 일로 적는다. 독자 추정만 있으면 `(추정)`을 붙인다. 블록에 수정이 둘이면 `왜(수정 N)`으로 나눈다.
- 여러 문단에 걸친 진단(대비 구문 반복 등)은 고치는 문단 블록에 `왜`를 두고, 그대로 두는 다른 위치는 `왜` 줄 끝 괄호에 원문 구절로 적는다.
- 데스크가 편집자 제안을 줄이거나 바꿨으면 블록 끝 `조정:` 한 줄로 밝힌다.
- 바뀌는 문단은 수정 전·수정 후 모두 문단 전문을 인용 블록으로 낸다. 수정 후에서 지운 말은 `~~ ~~`, 넣은 말은 `** **`로만 표시하고 나머지는 원문 그대로 둔다.
- 그대로인 문단은 연속 구간을 한 줄로 묶어 번호와 첫 구절 15자 안팎만 적는다. 지킬 문장이 있는 문단은 `(지킬 문장)`을 붙인다.
- 수정 후 문장은 반영 단계에서 글자 그대로 쓰인다. 2/4에 낸 문장과 3/4 결과가 달라지면 안 된다.
- 기본 표시는 추천 반영 항목과 작가 판단 항목을 모두 넣은 상태다.
- 저자 답에 따라 문장이 갈리면 A안을 블록에 넣고 B안은 블록 아래 한 줄로 적는다.
- 작가가 `수정 N 전문 보여줘`나 `문장 단위로 보여줘`라고 하면 그 수정만 문장 단위 전후 표(수정 전 / 수정 후 행)로 다시 낸다. `진단 근거 보여줘`면 1단계 진단 기록을 낸다.
- 필수 물음은 블록 보기 위에 따로 세운다. 물음마다 답이 어느 수정의 어떤 문장을 바꾸는지 화살표로 적는다. 선택 물음은 블록 보기 아래 한 줄로 둔다.
- 추천은 데스크 의견이고 결정은 작가가 한다.

- 단순 교체로 풀리지 않는 구조 문제는 영향받는 도입·전환·마무리를 함께 적는다.
- 충돌하는 대안은 섞지 않고 하나를 추천한다.
- 용어집 적용(호칭 통일·약어 삭제·영문 병기)은 `ED-용어` 한 이슈로 묶는다. High·Mid 상한 밖에서 관리한다.
- 한 이슈에는 등급 하나만 붙인다. 제안이 `High+Mid`나 '중·하' 같은 다른 등급으로 오면 High·Mid로 고쳐 고정하거나 두 이슈로 쪼갠다.
- 같은 문장을 고치는 제안이 둘 이상이면 하나로 합쳐 ID 하나를 매긴다.
- 이슈의 표현 강도가 저자 답변에 달려 있으면 `연결: Q번호`를 적는다.

이슈표 아래에 `저자 확인` 칸을 따로 둔다. 비어 있으면 `없음`으로 적는다. 범위 잠금 모드에서 범위 밖에 High급 문제가 보이면 고치지 않고 `범위 밖 후보: 위치 — 한 줄`로 함께 적는다.

```text
저자 확인
Q1. 3문단 — 수강생이 물은 사례는 AI 초안이 넣은 것인가, 직접 넣고 출처를 잊은 것인가
Q2. 2문단 — "70% 줄었다"는 무엇을 기준으로 잰 시간인가
```

작가에게는 저자 확인을 `저자에게 물을 것: 1) … 2) …` 한 줄로 낸다(위 블록은 내부 기록 형식). 이슈표 끝에 제안 관문 추천 요청과 다른 요청을 붙이고 멈춘다. `지금 정할 것` 줄은 머리 줄 바로 아래에만 둔다.

선행이 걸린 이슈만 골랐으면 반영 전에 짝을 알린다 — `ED-03은 ED-01을 전제로 합니다. ED-01 없이 넣으면 (위치)의 연결이 끊깁니다.` 사용자가 그대로 원하면 반영하고 끊긴 자리는 `구체화 필요`로 남긴다.

`진단만`이면 2단계에 오지 않고 1단계 진단 기록으로 끝낸다. 일괄 개선이면 High 전부와 판단 강도를 바꾸지 않는 Mid만 골라 3단계로 넘어가고, 고른 목록을 출력에 밝힌다.

완료 기준: 각 현재 문장을 원고에서 찾을 수 있고, 승인 전 변경 0건이며, 적용 대상이 명확하다.
